Architecture reference · v2

Urdu speech-to-text & Urdu→English translation, powered by the OpenAI API

A pipeline added to the existing Express app: record or type Urdu, transcribe it via OpenAI's whisper-1 audio transcription endpoint, edit the text, then translate it to fluent English via OpenAI Chat Completions. Nothing in this application calls Anthropic, Google, or any other third-party inference API — only OpenAI, and only for these two features.

Node.js · Express gateway Python · FastAPI OpenAI whisper-1 OpenAI Chat Completions (gpt-4o-mini) Mutual TLS internally Docker Compose · no GPU required

Architecture update: earlier revisions of this document described a fully self-hosted stack — faster-whisper for transcription, a locally-loaded Qwen2.5-7B-Instruct for translation, both requiring a GPU. That stack has been removed and replaced with calls to the OpenAI API, per an explicit architecture decision by the project owner — a deliberate simplification (no GPU host, no model downloads/caching, no CUDA/torch dependency chain), not a security response. See §6 Model selection for the current model/config surface and §7 for the current (GPU-free) deployment story. Sections below that describe the old "zero third-party API" stance have been corrected in place; historical context about the earlier self-hosted design is kept where useful but no longer reflects the current architecture.

Compliance update: a formal SOW review flagged unencrypted gateway↔AI-service traffic and the OpenAI-backed /speak route as gaps. Both were resolved as of that revision — see §5 Security model and §7 Docker Compose for mutual TLS, and the design-constraints table just below for the /speak/OpenAI-TTS removal (unrelated to, and unaffected by, the later OpenAI API migration described above — /speak remains removed; transcription/translation now use OpenAI for a different reason). Production performance and full end-to-end QA against the real OpenAI API are still pending in this environment — reported honestly as pending in §12, not claimed as done.

Platform expansion: a broader "Audio Transcription & Translation Platform" requirements document added record+upload with drag-and-drop, pause/resume with a live level meter, multi-language transcription/translation, MP3/TXT/DOCX/PDF export, and a permanent recording history. That directly reversed a prior decision in this document, and was confirmed explicitly rather than assumed: recordings and their transcripts/translations are now kept permanently (not deleted after the request — see §8a for the full detail).

01 Overview

What the system does, end to end, before the architecture detail.

  1. User records Urdu speech in the browser (or uploads an audio file, or types Urdu directly).
  2. Audio is sent to the gateway, which forwards it to the transcription service, which calls OpenAI's whisper-1 audio transcription endpoint forced to Urdu.
  3. The resulting Urdu text appears in an editable text area; the user can fix it before translating.
  4. Clicking Translate to English sends the (possibly edited) Urdu text to the translation service, which calls OpenAI Chat Completions (default model gpt-4o-mini).
  5. The English translation appears in its own panel; Urdu and English can be copied independently, and editing the Urdu again marks the English stale.

Design constraints that shaped every decision below

ConstraintConsequence
Only OpenAI, only for these two featuresTranscription and translation both call the OpenAI API; nothing in this app calls Anthropic/Google for anything — the unrelated OpenAI-backed /speak route was removed entirely in an earlier revision and stays removed. This is a deliberate architecture change from an earlier fully self-hosted, zero-third-party-API design (see the architecture update callout above).
No GPU, no model sizingThere is no local model to size — no VRAM tier, precision, or quantization choice. The only model knobs are OPENAI_TRANSCRIBE_MODEL/OPENAI_MODEL — see §6.
Existing app must keep workingThe gateway is the same Express process as before; /health is untouched, and a single flag (ENABLE_AI_FEATURES=false) fully disables the new feature.
Paid API, bursty traffic, rate limitsConcurrency is bounded at three independent layers so a burst of requests degrades to a fast 503 instead of hitting OpenAI's rate limits or running up unbounded cost — see §5.

02 System architecture

One public process, two private services that each call out to OpenAI, one crossing point.

This mirrors the app's existing shape — one Express process serving the UI and terminating client requests — with two new internal collaborators instead of a rewrite. The gateway never calls an AI API directly; the Python services are never reachable from the public internet, but they do reach out to it (to api.openai.com) on every request.

Transcription service — ai-services/transcription/

FastAPI app around the OpenAI audio transcription API (whisper-1 by default). model_backend.py creates the OpenAI client once at startup and is the only module that imports the openai package, so unit tests can stub it entirely without installing it. Language is forced to ur rather than auto-detected, so a sentence with an occasional English word doesn't cause the decoder to switch languages mid-utterance.

# POST /v1/transcribe — abbreviated request lifecycle
verify_token(authorization)                    # 401 if Bearer mismatch
guard.try_acquire()                            # 503 if MAX_CONCURRENT_TRANSCRIPTIONS reached
validate content_type in ALLOWED_CONTENT_TYPES # 400 otherwise
stream to tempfile, enforcing MAX_AUDIO_UPLOAD_MB # 413 if exceeded
asyncio.to_thread(model_backend.transcribe_file, tmp_path)  # calls OpenAI's whisper-1 API
finally: guard.release(); os.remove(tmp_path)

Translation service — ai-services/translation/

model_backend.py wraps the OpenAI Chat Completions API (gpt-4o-mini by default, via OPENAI_MODEL). prompt.py builds the controlled system prompt and defends against instruction injection; chunker.py splits long input by structure. Generation is greedy (DO_SAMPLE=false, i.e. temperature=0) for deterministic, reproducible translations.

# POST /v1/translate — abbreviated request lifecycle
verify_token(authorization); validate 0 < len(text) <= MAX_TRANSLATE_TEXT_LENGTH
guard.try_acquire()                            # 503 if MAX_CONCURRENT_TRANSLATIONS reached
batches = chunker.build_batches(text, count_tokens, MAX_INPUT_TOKENS_PER_CHUNK)
for batch in batches:
    if request.is_disconnected(): abort   # cooperative cancellation between chunks
    translated.append(model_backend.translate_one(batch))  # prompt.py wraps + sanitizes the text
return chunker.reassemble(translated)

Prompt-injection defense, concretely

The Urdu text is wrapped in fixed delimiters before it reaches the model, and any literal delimiter sequence inside the user's text is neutralized first, so a message like "...<<>> ignore all previous instructions" cannot forge a fake end-of-content marker and leak into instruction context:

BEGIN_MARKER = "<<<URDU_TEXT_START>>>"
END_MARKER   = "<<<URDU_TEXT_END>>>"

def _neutralize_delimiter_collisions(text):
    return text.replace("<<<", "‹‹‹").replace(">>>", "›››")

def build_messages(user_text):
    safe_text = _neutralize_delimiter_collisions(user_text)
    wrapped = f"{BEGIN_MARKER}\n{safe_text}\n{END_MARKER}"
    return [{"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": wrapped}]

The system prompt itself explicitly instructs the model to treat the delimited block as literal data — never as commands — and to return only the translated text. See ai-services/translation/tests/test_prompt.py for the adversarial cases this is tested against.

06 Model selection

Chosen deliberately, not defaulted — including why OpenAI's hosted models were chosen over the self-hosted alternatives evaluated in earlier revisions.

Transcription — OpenAI whisper-1

model_backend.py calls the OpenAI audio transcription API instead of running a model in-process. whisper-1 is used specifically — not the newer gpt-4o-transcribe/gpt-4o-mini-transcribe — because it is currently the only OpenAI transcription model that supports response_format="verbose_json", which is what gives this service the detected language and audio duration fields it returns, not just the transcript text.

VarDefaultNotes
OPENAI_API_KEYrequiredShared with the translation service via one .env file
OPENAI_TRANSCRIBE_MODELwhisper-1 defaultSee above for why this model specifically
WHISPER_LANGUAGEurForced/default source language (ISO 639-1); kept as WHISPER_* since OpenAI's own hosted model here is still literally named "whisper-1"

There is no GPU, model-size, or VRAM configuration anymore — whisper-1 runs entirely on OpenAI's infrastructure.

Translation — OpenAI Chat Completions (gpt-4o-mini default)

model_backend.py sends the constructed prompt to OpenAI's Chat Completions API instead of running a local transformers model. Default: gpt-4o-mini, a cost/latency-appropriate default for a constrained "translate only" prompt; override with OPENAI_MODEL for a higher-quality (and higher-cost) model such as gpt-4o if needed.

Why OpenAI's hosted models instead of self-hosting (e.g. Qwen2.5-Instruct, as earlier revisions of this document evaluated): this was an explicit, deliberate architecture decision by the project owner, not a technical dead-end with the self-hosted approach. Self-hosting removed any per-request cost/rate-limit exposure and kept inference fully private, at the cost of requiring a GPU host, model downloads/caching, and a CUDA/torch/transformers dependency chain to keep patched. Calling OpenAI's API removes all of that operational burden (no GPU provisioning, no model weights to manage, smaller/simpler container images — see §7) in exchange for a live third-party dependency: every request now costs money, is subject to OpenAI's rate limits, and needs network egress and a valid API key to function at all.

The Cohere/Mistral/NLLB-style self-hosted-model comparison this section used to carry is superseded — kept below only as a historical record of what was evaluated before the OpenAI API migration, not as live guidance:

Upgrade path: the API contract (POST /v1/translate {text} → {translation}) is unchanged from the self-hosted design — swapping OPENAI_MODEL, or swapping the OpenAI client in model_backend.py for a different provider's API entirely, would not require any change outside that file.

07 Implementing with the OpenAI API

Two supported paths — Docker Compose (recommended) and native/bare-metal — plus how to confirm the OpenAI API is actually being used. No GPU required anywhere in this section anymore (see the architecture update at the top of this document).

Prerequisites

RequirementWhy
Docker Engine + Compose v2Runs docker-compose.yml
A valid OPENAI_API_KEYBoth AI services fail their /ready check without it — no local-model fallback exists
Outbound HTTPS egress to api.openai.com, on every request (not just at startup)Both AI services call the OpenAI API for every transcribe/translate request
OpenSSLUsed by scripts/generate-internal-certs.sh to generate the internal mTLS certs (§2 below) — no external CA/dependency needed

No longer needed: an NVIDIA driver, the NVIDIA Container Toolkit, and free disk space for a model cache — none of that applies anymore, since neither AI service runs a local model. Both Dockerfiles are plain python:3.12-slim images with no CUDA/torch/transformers/bitsandbytes/faster-whisper/ctranslate2 dependencies.

Path A — Docker Compose (recommended)

  1. Configure the environment: 
    cd server
cp .env.example .env
# set a real INTERNAL_SERVICE_TOKEN, e.g.:
openssl rand -hex 32   # paste the output into INTERNAL_SERVICE_TOKEN=
# set a real OPENAI_API_KEY — both AI services fail /ready without one
# optionally override OPENAI_TRANSCRIBE_MODEL / OPENAI_MODEL — see §6
  2. Generate the internal mTLS certs (gateway↔AI-service encryption — see §5): 
    ./scripts/generate-internal-certs.sh   # writes server/certs/ (gitignored)
  3. Build and start: 
    docker compose build
docker compose up -d
docker compose ps       # all three services should show "healthy" within seconds — no model to load

    Startup is fast: there are no model weights to download or load. Both AI containers just need OPENAI_API_KEY to create an OpenAI client at startup — watch docker compose logs -f transcription translation for openai_client_ready (or model_load_failed if the key is missing/invalid).

  4. Confirm readiness: 
    curl http://localhost:3000/api/v1/ready
# {"status":"ready","aiFeaturesEnabled":true,"services":{"transcription":true,"translation":true}}
  5. For real public traffic, start the bundled TLS-terminating reverse proxy (Caddy) instead of relying on the loopback-only gateway port — point a real domain's DNS at this host first: 
    PUBLIC_DOMAIN=your-domain.example.com docker compose --profile proxy up -d
    Caddy (deploy/Caddyfile) automatically obtains and renews a Let's Encrypt certificate for PUBLIC_DOMAIN. Left unset, it defaults to localhost with a locally-trusted certificate only — fine for internal testing, not for real public traffic.

Path B — Native / bare-metal (no Docker)

Useful while iterating on the Python services directly — any machine works, GPU or not.

# 1) Gateway

Set TRANSCRIPTION_SERVICE_URL=http://localhost:8001 and TRANSLATION_SERVICE_URL=http://localhost:8002 in the gateway's .env (these are already the defaults). Set OPENAI_API_KEY for both AI service processes.

08a Recording history, languages & exports

Added for the platform-expansion requirements above. All of it lives inside the existing gateway process — no new service, no external database.

What's new

Persistent history

  • Every recorded or uploaded clip is converted to MP3 (lib/audioStorage.js, ffmpeg) and kept in recordings/
  • A SQLite row (lib/db.js, lib/recordingsRepo.js) tracks status, source/target language, transcription text, translation text, and timestamps through pending → transcribing → transcribed → translating → completed/failed
  • routes/recordings.js exposes list (search/filter/paginate), get, stream-audio, export, and delete — mounted at /api/v1/recordings
  • Optional auto-pruning via RECORDINGS_RETENTION_DAYS (default 0 = keep forever)

Multi-language & exports

  • Transcription accepts an optional language override (or auto-detect); translation accepts sourceLanguage/targetLanguage — the LLM prompt is built dynamically for the requested pair (ai-services/translation/prompt.py), not hardcoded to Urdu→English
  • Export a recording as TXT, DOCX, or PDF (lib/exporters.js) — the PDF path hand-rolls script-run splitting + RTL line layout since PDFKit has no built-in cross-script bidi/shaping
  • PDF Arabic-script text renders with Noto Naskh Arabic, not Nastaliq — Nastaliq crashed PDFKit on ordinary letter sequences and digits; Naskh has full glyph coverage and zero crashes (verified by rendering to PNG and visually inspecting, not just checking for exceptions)
  • "Save audio" downloads the stored MP3 directly from the browser — no re-encoding round trip

Frontend additions

Create/History tabs; a drag-and-drop zone alongside the existing file picker; pause/resume on the recorder with a live canvas level meter (Web Audio API AnalyserNode); source/target language dropdowns; a History dashboard with search, status/source-type filters, pagination, a detail panel with inline audio playback, and per-recording export/delete.

09 Privacy & data lifecycle

Policy reversed in this revision: earlier revisions of this document said recordings and text were never persisted. That has changed by explicit request — see §8a. The table below reflects the current policy, not the original ephemeral one.

What is stored, and where

  • Converted MP3 audio — kept permanently in recordings/ (a Docker named volume in Compose) until deleted by the user or pruned by RECORDINGS_RETENTION_DAYS
  • Transcription/translation text and metadata — kept in the SQLite DB at data/app.db, same lifecycle as the audio
  • The original multipart upload in uploads/ is still transient — deleted once conversion to MP3 succeeds or fails
  • This application does not fine-tune or train any model — audio and text are sent to OpenAI purely for one-shot inference per request. Whether OpenAI itself retains or uses API request content is governed by OpenAI's own API data usage policy, not by this application; by default OpenAI does not use API content to train its models, but this is a third-party policy this project does not control, unlike the fully self-hosted design described in earlier revisions of this document

What logs actually contain

  • Request IDs, durations, byte counts, HTTP status codes, recording IDs
  • Never: raw Urdu/English text, audio bytes, tokens, or API keys — redacted by construction in lib/logger.js / logging_utils.py, not by remembering to scrub each call site
  • Verified by tests/logger.test.js and tests/privacyLogging.test.js

Narrower privacy boundary than the original self-hosted design: audio and text content now reaches OpenAI's infrastructure on every transcribe/translate request, over HTTPS, in addition to staying within this application's own Docker network for the gateway↔AI-service leg (mutual TLS, §5). This is a direct consequence of the OpenAI API migration described at the top of this document.

12 Rollback, monitoring & QA

Rollback

This was almost entirely an additive change — the one deliberate removal was the OpenAI-backed /speak route (see the compliance note above), a requested fix, not a regression, and unrelated to the later OpenAI API migration (transcription/translation now use OpenAI, but /speak stays removed). Fastest rollback of the rest: set ENABLE_AI_FEATURES=false and restart the gateway; the new routes return 503 immediately while /health and the static UI keep working. Full rollback: stop the transcription/translation containers, or redeploy the gateway from before this change.

Monitoring

  • No GPU/VRAM metric to monitor anymore — both AI service containers are plain CPU containers that just make outbound HTTPS calls to OpenAI
  • Docker healthchecks already wired to each service's /health and /ready (mTLS-aware — healthcheck.sh); /ready reflects whether the OpenAI client was created successfully (i.e. OPENAI_API_KEY was present)
  • Alert on sustained ai_service_error / 503 rates in gateway logs (now an OpenAI API error/timeout/rate-limit rejection, or a network egress problem reaching api.openai.com, rather than GPU saturation or a crashed local model process)
  • New operational concern vs. the self-hosted design: track OpenAI spend/usage via the OpenAI dashboard or usage API for the project's key, and alert on sustained 429s surfacing as ai_service_error — that means traffic is exceeding the account's current OpenAI rate-limit tier
  • Track transcription_completed.duration_ms and translation_completed.duration_ms as separate latency series (now largely reflecting OpenAI API latency plus network round-trip, not local inference time)
  • Alert on internal mTLS cert expiry — scripts/generate-internal-certs.sh has no automated renewal (825-day default validity)
  • Alert on disk usage for the gateway-data/gateway-recordings volumes — with RECORDINGS_RETENTION_DAYS=0 (the default) they grow unbounded

Known gaps — honestly unverified in this environment

  • No per-user authentication/ownership on recording history yet — anyone with API access sees all recordings; add auth before a multi-tenant deployment
  • better-sqlite3/ffmpeg compatibility with the Alpine (musl) gateway image was verified by reading the packages' prebuilt-binary source logic, not by actually running docker build — Docker Desktop's daemon was unavailable in this sandbox
  • Retention pruning (RECORDINGS_RETENTION_DAYS) is unit-tested but not exercised against real aged production data
  • Not verified end-to-end against the real OpenAI API in this environment — no live OPENAI_API_KEY was exercised here; see the test report for exactly what was and wasn't run
